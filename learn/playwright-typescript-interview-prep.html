1. Playwright basics

This section is the foundation everything else rests on. Work through it first. Each topic gives the content, then self-check questions whose answers an interviewer would expect within a sentence or two.

1.1 What Playwright is and how it drives a browser

Playwright is a browser automation and test-running framework from Microsoft. It ships two things that are easy to confuse: the Playwright library for driving browsers, and Playwright Test (@playwright/test), the test runner with fixtures, parallelism, reporters and assertions. In interviews, "Playwright" almost always means the test runner.

It drives Chromium, Firefox and WebKit from a Node.js process over a single persistent connection, using each browser's own automation protocol. Two consequences matter and both come up in interviews: it can create many cheap isolated browser contexts, and it can observe and intercept network traffic below the page, which an in-browser runner cannot do as easily.

What is the difference between the Playwright library and Playwright Test?

The library automates browsers and can be embedded in any Node.js program, for example a scraping or monitoring script. Playwright Test adds the test runner: fixtures, parallel workers, projects, retries, web-first assertions, reporters, traces and the CLI. Installing @playwright/test gives you both; you do not install playwright alongside it.

Which browsers does Playwright support, and does it use the real browsers?

Chromium, Firefox and WebKit, downloaded as Playwright-managed builds so versions are pinned and reproducible. It can also run against installed branded channels such as Google Chrome and Microsoft Edge via the channel option, which is what you use when a stakeholder insists on testing "real Chrome". WebKit is the practical way to get Safari engine coverage on Linux CI.

1.2 Setting up a project

npm init playwright@latest        # scaffolds config, example test, CI workflow
npx playwright install            # download browsers
npx playwright install chromium --with-deps   # CI: only what you need

Scaffolding produces playwright.config.ts, a tests/ folder and optionally a GitHub Actions workflow. TypeScript works with no build step: name a file .spec.ts and the runner transpiles it. That is a genuine differentiator worth mentioning, because it removes the Babel or ts-node plumbing older stacks needed.

Do you need to compile TypeScript before running Playwright tests?

No. The runner transpiles test files on the fly and respects tsconfig.json for baseUrl and paths aliases. It does not type-check as it runs, which is why a mature pipeline adds tsc --noEmit as a separate gate.

1.3 Anatomy of a test

import { test, expect } from '@playwright/test';

test('customer can sign in', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('User name').fill('anna');
  await page.getByLabel('Password').fill('secret');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByText('Welcome, Anna')).toBeVisible();
});

The destructured { page } is a fixture. Asking for it tells the runner to create an isolated browser context and a page for this test, and to tear both down afterwards. Almost everything is asynchronous, so almost everything is awaited.

Why is page passed as an argument instead of being a global?

Because it is a fixture created per test. That is what guarantees isolation: every test gets a fresh context with its own cookies, storage and permissions, which is what makes safe parallel execution possible. Globals would force shared state and serial runs.

1.4 Browser, context and page

  • Browser — one launched browser process, shared across tests in a worker to save start-up cost.
  • BrowserContext — an isolated profile, effectively a fresh incognito session. Own cookies, local storage, permissions, geolocation. Cheap to create.
  • Page — a tab inside a context. A context can hold several pages, which is how you test multi-tab and multi-user flows.
How would you test two users interacting, for example an approver and a requester?

Create two contexts from the same browser, each with its own storage state or login, and a page in each. They are fully isolated from one another, so one can submit and the other can approve inside a single test without any cookie bleed.

1.5 Locators

A locator is a lazy description of how to find elements. It is re-resolved immediately before every action, so a re-render between two lines of your test does not produce a stale element error. This is the single biggest day-to-day difference from Selenium's WebElement.

Recommended priority, highest first:

  1. getByRole('button', { name: 'Sign in' }) — matches how users and assistive technology perceive the page.
  2. getByLabel() for form controls.
  3. getByPlaceholder(), getByAltText(), getByTitle().
  4. getByTestId() — an explicit contract with developers; the attribute is configurable via testIdAttribute.
  5. page.locator('css') or XPath — last resort, because both couple tests to DOM structure.
// chaining and filtering instead of brittle CSS chains
const row = page.getByRole('listitem').filter({ hasText: 'Product 2' });
await row.getByRole('button', { name: 'Add to cart' }).click();

// alternatives and combinations
page.getByRole('button').and(page.getByTitle('Subscribe'));
newEmailButton.or(securityDialog).first();
page.locator('button').visible();
What is strict mode?

Locators are strict by default: if an action targets a locator that matches more than one element, Playwright throws instead of silently acting on the first. Multi-element operations such as count() are fine. Resolve a violation by narrowing with role plus accessible name, chaining inside a container, or filter(). Reaching for first() or nth() is an admission that the locator does not express intent.

Why prefer role locators over CSS?

They survive styling and markup refactors, they read like the user's experience rather than the implementation, and they give early feedback on accessibility because a missing accessible name breaks the locator. They do not replace an accessibility audit, but they surface obvious gaps continuously.

Does Playwright handle shadow DOM and iframes?

Locators pierce open shadow roots by default; the exceptions are XPath, which does not pierce, and closed shadow roots, which are unsupported. For iframes use frameLocator(), which waits for the frame and then scopes the search inside it.

1.6 Actions

await locator.click();            await locator.dblclick();
await locator.fill('text');       await locator.clear();
await locator.check();            await locator.setChecked(true);
await locator.selectOption('Red');
await locator.setInputFiles('invoice.pdf');
await locator.hover();            await locator.dragTo(target);
await page.keyboard.press('ControlOrMeta+S');

fill() sets the value in one operation and is the default choice. pressSequentially() types character by character and is only for inputs with special key handling, such as autocomplete widgets that react to each keystroke.

When would you use pressSequentially() instead of fill()?

Only when the application reacts to individual key events — typeahead search, input masks, character counters driven by keydown. Otherwise fill() is faster and less flaky. The old type() method is deprecated.

1.7 Auto-waiting and actionability

Playwright performs actionability checks before acting and retries until they pass or the action times out. Knowing this list by name is a strong signal in interviews.

  • Attached — present in the DOM.
  • Visible — non-empty bounding box, not visibility: hidden.
  • Stable — has stopped moving between animation frames.
  • Receives events — nothing else overlays the hit point.
  • Enabled — not disabled.
  • Editable — additionally required for typing.

Consequence: explicit sleeps are unnecessary and harmful. page.waitForTimeout() exists for debugging only.

Why does an action still fail even though the element is on screen?

Usually because an actionability check other than visibility is failing: an overlay, a cookie banner or a toast intercepting the click point, or an animation still running so the element is not stable. The timeout error includes an actionability log naming the check that blocked, and the trace shows the DOM at that moment.

What do you do about a cookie banner that appears unpredictably?

page.addLocatorHandler() registers a dismissal handler that fires whenever the interstitial appears, with a times limit. Better still, suppress it at source with a pre-set cookie or a route stub so no test spends time on it.

1.8 Assertions

Assertions on a locator or page are web-first: they poll and retry until the condition holds or the expect timeout expires. Assertions on plain values evaluate once.

await expect(page.getByText('Welcome')).toBeVisible();   // retries
await expect(page.getByRole('listitem')).toHaveCount(3);
await expect(page).toHaveURL(/dashboard/);
await expect(response).toBeOK();

expect(await locator.isVisible()).toBe(true);            // anti-pattern: no retry

await expect.poll(async () => (await api.get('/status')).status()).toBe(200);
await expect(async () => { /* several checks */ }).toPass();
await expect.soft(locator).toHaveText('Success');        // does not stop the test
What is the difference between a web-first assertion and a plain one?

A web-first assertion re-queries the element and re-evaluates the condition until it passes or times out, which absorbs normal asynchronous rendering. A plain assertion samples a single instant, so it turns ordinary latency into a failure. The classic bug is putting await inside expect() rather than in front of it.

When are soft assertions appropriate?

When you want a full picture from one run — validating many fields on a summary page, or an accessibility sweep. Never for preconditions, because continuing after a failed precondition produces a cascade of misleading downstream failures.

1.9 Organising tests: hooks, describe, tags

test.describe('onboarding', () => {
  test.beforeEach(async ({ page }) => { await page.goto('/onboarding'); });

  test('happy path', { tag: ['@smoke', '@kyc'] }, async ({ page }) => { /* ... */ });

  test('sanctions hit', {
    annotation: [{ type: 'issue', description: 'JIRA-1234' }],
  }, async ({ page }) => { /* ... */ });
});

test.skip(condition, 'reason');
test.fixme();
test.slow();

Tags drive selection with --grep @smoke, which is how you map a Playwright suite onto the risk-based test selection you already run in Jira and Xray.

Hooks or fixtures?

Hooks are fine for trivial shared navigation inside one file. Fixtures are the real mechanism: they keep setup and teardown together, are reusable across files, are created only when a test asks for them, compose with each other and are type safe. Anything expensive belongs in a worker-scoped fixture. Covered in depth in the interview bank.

1.10 The configuration file

import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  workers: process.env.CI ? 2 : undefined,
  retries: process.env.CI ? 2 : 0,
  reporter: process.env.CI ? 'blob' : 'html',
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    testIdAttribute: 'data-test',
  },
  projects: [
    { name: 'setup', testMatch: /auth\.setup\.ts/ },
    { name: 'chromium', use: { ...devices['Desktop Chrome'] }, dependencies: ['setup'] },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] }, dependencies: ['setup'] },
  ],
  webServer: { command: 'npm run start', url: 'http://localhost:3000',
               reuseExistingServer: !process.env.CI },
});
What is a project in Playwright?

A named run configuration with its own options. Projects are how you do a browser matrix, a mobile viewport run, or a staging-versus-local split. dependencies makes one project run before another, which is how an authentication setup project feeds storage state to the browser projects. teardown is its mirror image for cleanup.

Which timeouts exist and which one bit you?

Test timeout for the whole test, expect timeout for web-first assertions, action timeout for individual clicks and fills, navigation timeout for page loads, plus separate timeouts for fixtures and for webServer startup. Raising the test timeout to hide a slow assertion is a common mistake; the right move is usually to fix the wait or to raise only the specific expect.

1.11 Running tests from the CLI

npx playwright test                       # everything
npx playwright test login.spec.ts:12      # one test by line
npx playwright test --project=chromium
npx playwright test --grep @smoke
npx playwright test --headed --workers=1
npx playwright test --ui                  # UI mode with watch
npx playwright test --debug               # Inspector, step through
npx playwright test --trace on
npx playwright test --last-failed
npx playwright test --shard=1/4
npx playwright show-report
npx playwright show-trace trace.zip
npx playwright codegen https://example.com

1.12 Debugging tooling

  • UI mode (--ui) — the authoring environment: watch mode, time-travel through actions, live locator editing, filter by tag.
  • Trace viewer — the CI post-mortem tool. Timeline, DOM snapshot before and after every action, network panel, console, source and attachments. Traces open at trace.playwright.dev, which is a local progressive web app, so nothing is uploaded.
  • Inspector (--debug) — step through, with actionability logs and live locator highlighting.
  • Codegen and the VS Code extension — use for picking locators and exploring, not for producing final tests.
Why not record all your tests with codegen?

Recordings capture a click path, not intent. They produce no page objects, no fixtures, no data setup and no meaningful assertions, so they rot on the first refactor. Codegen is excellent for discovering the locator Playwright would choose and for exploring an unfamiliar page.

1.13 Reporters and artifacts

list and line for local runs, html for humans, junit for pipeline and test-management integration, blob for sharded runs which are then combined with merge-reports into one HTML report. Artifacts to configure deliberately: traces, screenshots and video, each with modes such as on-first-retry, only-on-failure and retain-on-failure. Tracing everything is expensive, so do not.

1.14 TypeScript you need on day one

  • async / await and why a missing await is a silent bug.
  • Type annotations, interface versus type, union types for things like a customer risk category.
  • Generics, because test.extend<TestFixtures, WorkerFixtures> uses them.
  • Optional chaining, nullish coalescing, strictNullChecks.
  • unknown over any when parsing responses.
  • ESLint with @typescript-eslint/no-floating-promises, plus tsc --noEmit in CI.

Basics checkpoint. Before moving to the interview bank you should be able to, without notes: name the actionability checks; explain why a locator is not a stale element; explain what a browser context isolates; and say what trace: 'on-first-retry' does and why it is not 'on'.

2. Interview question bank

Each block gives the question, what is actually being tested, and the spine of a strong answer. Target sixty to ninety seconds, then stop and offer to go deeper.

2.1 TypeScript

Why TypeScript for test automation rather than plain JavaScript?

Tested: whether you chose the language or inherited it.

Compile-time feedback on page-object and fixture contracts, IDE discoverability of a large API, safe refactoring across a big suite, and typed test data that prevents invalid states being constructed. Name the cost honestly: build configuration, and a learning curve for manual testers joining the suite.

What is the difference between interface and type?

Interfaces are open to declaration merging and read naturally for object shapes; type aliases express unions, intersections, mapped and conditional types. The distinction matters less than consistency — say which convention your team picked and why.

Where have you used generics in a test framework?

A typed API client where the response type is a parameter; typed data builders; and test.extend<TestFixtures, WorkerFixtures>, where the two parameters separate test-scoped from worker-scoped fixture types so the runner knows which lifetime to give each.

What goes wrong if you forget an await?

The promise floats. The action or assertion never completes within the test, so a test can pass while doing nothing, and the failure surfaces later as an unhandled rejection attributed to an unrelated test. Prevention is tooling, not discipline: the @typescript-eslint/no-floating-promises rule plus tsc --noEmit as a pipeline gate.

unknown versus any?

any disables checking and spreads through the codebase; unknown forces you to narrow before use. Parse API responses into unknown and narrow, or type the request call generically so the response is typed at the call site.

Quick-fire: optional chaining and nullish coalescing; readonly and as const; enum versus union of string literals; Partial, Pick, Omit, Record; why Promise.all on locator actions is usually wrong; how tsconfig path aliases are resolved by the runner.

2.2 Playwright fundamentals

How does Playwright differ from Selenium WebDriver, and from Cypress?

Tested: whether you understand the tools or repeat marketing lines.

Selenium speaks the W3C WebDriver protocol to a driver per browser. Playwright drives browsers directly over a single persistent connection using browser-specific protocols, which enables cheap contexts, network interception below the page, and built-in auto-waiting. Cypress executes inside the browser alongside the application, giving excellent debugging but historically constraining multi-origin, multi-tab and cross-browser work. Selenium's enduring strength is language and grid ecosystem breadth. Since you have shipped in all three, close by saying which you would pick for which context.

Explain browser, context and page.

One browser process, many contexts, each an isolated profile with its own cookies, storage and permissions, each holding one or more pages. Contexts are why isolation is cheap and why parallel workers do not leak state into one another.

What is a locator, and why is it better than an element reference?

A locator is a lazy description re-resolved immediately before every action, so a re-rendered DOM does not produce a stale element error. An element handle points at one node at one moment in time and goes stale.

What does Playwright wait for before it clicks?

Actionability checks: attached, visible, stable meaning it has stopped moving between animation frames, able to receive events meaning nothing overlays the hit point, and enabled. Typing additionally requires editable. If a check fails it retries until the action timeout, and the error log names the blocking check.

What is strict mode and how do you resolve a violation?

Any action on a locator matching more than one element throws. Fix by narrowing with role plus accessible name, chaining within a container, or filter(). Using first() or nth() admits the locator does not express intent; acceptable only for genuinely ordinal lists.

Locator strategy, in priority order, and why?

Role with accessible name first, because it matches what users and assistive technology perceive and doubles as a light accessibility check. Then label, placeholder, alt text, title. Then test ids as an explicit contract negotiated with developers. CSS last, XPath effectively never, because both couple tests to DOM structure. Mention that the test id attribute is configurable.

Web-first assertions versus plain assertions?

expect(locator).toBeVisible() polls and retries until the expect timeout; expect(value) evaluates once. The classic anti-pattern is expect(await locator.isVisible()).toBe(true), which samples a single instant. For non-locator conditions use expect.poll or expect.toPass.

Quick-fire: toHaveText versus toContainText; asserting a list with an array argument; toHaveCount; toBeAttached versus toBeVisible; toBeInViewport; expect.configure for a slower assertion timeout; locator.describe for readable traces; shadow DOM support and the XPath exception; frameLocator for iframes.

2.3 Framework design

Walk me through the structure of your Playwright framework.

Tested: whether the structure is reasoned or copied.

Specs express intent only; fixtures supply the environment and collaborators; page and component objects hold interaction knowledge; an API client arranges state; config holds the project matrix and timeouts. Finish by naming one thing you would change today and why — that sentence is what separates a builder from a user.

Fixtures or beforeEach hooks?

Fixtures keep setup and teardown in one place, are reusable across files, are created only when a test asks for them, compose with each other, and are type safe. Hooks are fine for trivial shared navigation. Worker fixtures exist for anything expensive enough to create once per worker.

Give an example of a worker-scoped fixture.

A per-worker test account derived from the worker index, created in setup and deleted in teardown, so parallel tests never fight over the same customer record. Note that a worker fixture has its own timeout and that workers are restarted after a failure to guarantee a clean environment.

How do you handle authentication?

A setup project logs in once, saves storageState to a file, and is declared as a dependency of the browser projects, so every test starts authenticated. Where tokens live in IndexedDB rather than cookies, save that too. For tests that mutate account state, use a per-worker account instead of one shared login. Keep a small number of tests that exercise the real login UI, because storage state bypasses it.

Do page objects contain assertions?

State a position and the trade-off. Assertions in specs make failures read as violated intent and keep page objects reusable; assertions inside page objects reduce duplication for repeated compound checks. A common middle ground is exposing locators and small query methods, asserting in the spec, with a few named verification helpers for heavily repeated checks.

How do you keep a large suite maintainable?

A shared locator contract with developers; component objects for repeated widgets; fixtures instead of inheritance; tags for selection; a naming convention tied to requirements so coverage maps back to Jira and Xray; a review rule that every new test declares its level and its data needs; and a recurring pass on the slowest and flakiest tests.

How do you decide what belongs in an end-to-end test at all?

Risk, expressed as the classic test-shape argument. End-to-end tests cover journeys that cross services and carry business or regulatory consequence, such as onboarding with screening. Field validation, edge cases and permutations belong at API or component level where they run in a fraction of the time. This is where your test-management background is the differentiator — do not answer it as a tool user.

Quick-fire: test.use for per-file options; option fixtures with option: true for parameterised projects; mergeTests and mergeExpects; box: true to hide helper noise in reports; auto fixtures as global before and after hooks; project dependencies and teardown; snapshotPathTemplate.

2.4 Reliability and flakiness

A test passes locally and fails on CI. Walk me through your process.

Tested: forensic discipline. This is the single most predictive question in the set.

Reproduce from evidence, not from guesses. Open the trace from the failing run, find the failing action, compare the DOM snapshot before and after, check the network panel for a pending or failed call, check the console for application errors. Then classify: environment difference, timing, data collision, test pollution, or a genuine product defect. Fix the cause. Retries are a safety net for infrastructure noise, never a fix, and a test that keeps needing them should be quarantined and tracked as a defect.

Name the categories of flakiness you have actually hit.

DOM races on re-render; shared mutable test data; animations and transitions; time-dependent logic such as session expiry and cut-off times; unstubbed third-party calls and cookie banners; test ordering dependencies; resource contention from too many workers on a small runner; expired authentication state; latency differences between local and CI.

How do you test time-dependent behaviour?

The clock API. Install a fixed time, let the page load, then fast-forward or pause at a specific instant and assert. This removes sleeps entirely from session-timeout, cut-off-time and scheduled-task scenarios, which maps directly onto banking flows.

Two tests both edit the same customer. What do you do?

First choice: give each test its own data, derived from the test id or created per test through the API. If the resource is genuinely singular — a global setting, an external sandbox — declare a named lock so those tests never run concurrently while everything else stays parallel. Serial mode is a last resort, because a failure skips the rest of the group.

How do you stop tests leaking state into each other?

Each test already gets its own browser context, so cookies and storage are isolated. The leaks that remain are outside the browser: backend records, files written to a shared path, and module-level variables. Use per-test identifiers, testInfo.outputPath for files, and never hold state in module scope.

2.5 CI, scale and reporting

How do you run Playwright in CI?

Linux runners; install only the browsers actually needed, or use the official Docker image; type-check and lint gates before tests; smoke suite on every pull request; full regression sharded on a schedule; traces on first retry; HTML report and traces published as artifacts; results fed back into the test-management tool. Anchor this in the GitHub Actions and Jenkins pipelines you have already run.

Your suite takes too long. What do you do, in order?

Measure first, using the report's slowest-test view rather than intuition. Then: remove waits and sleeps; move coverage down the stack from UI to API; arrange state through the API instead of the UI; enable full parallelism; tune worker count against runner CPU; shard across machines; cut redundant cross-browser runs to the risk-justified minimum; cache dependencies and browsers; disable video and trace-everything modes.

How do you get one report out of a sharded run?

Each shard emits a blob report and uploads it as an artifact; a final job merges them with merge-reports into a single HTML report. Worth adding that the merged report can group by file and shows a timeline across shards.

Workers, shards and fullyParallel — explain the difference.

Workers are parallel processes on one machine. fullyParallel allows tests within a single file to spread across workers rather than running in declaration order. Sharding splits the suite across separate machines. They compose: shards multiply the available worker count.

How do you report quality status to stakeholders?

Lead with the nine years here. Automated pass rate is not quality. Talk about coverage against requirements, risk areas, defect trends by severity, flaky-test debt, and release readiness with explicit known risks. You maintained a quality metrics matrix at Model N — use it as the example.

2.6 API, network and data

When do you test through the API instead of the UI?

Whenever the assertion does not depend on rendering. Use the API to create customers, seed screening results and reach the state under test, then use the UI to assert what a user sees. Faster, less brittle, and it keeps end-to-end tests focused on integration risk.

Difference between the request fixture and page.request?

page.request shares the page context's cookies and storage state, so it acts on behalf of the logged-in user. The standalone request fixture is an isolated context, which is what you want for pure API tests or for arranging state before a browser exists.

How do you mock a third-party dependency?

Route the URL pattern and fulfil with a controlled response. For a partial change, fetch the real response inside the handler, modify the JSON and fulfil with it. For a large surface, record a HAR once and replay it. Rationale: you only test what you own, and an unstable external sandbox causes failures that teach you nothing.

You already have Bruno and RestAssured suites. Why put API calls in Playwright too?

Different purposes. The dedicated API suites own contract and behaviour coverage. Playwright's request context exists to arrange and verify state around UI journeys. Duplicating full API coverage inside the UI suite would be waste. This answer shows judgement rather than tool enthusiasm, which is exactly what a senior interviewer is listening for.

How do you manage test data for a regulated domain?

Synthetic data only, never production personal data; typed builders producing valid-by-construction records; per-test or per-worker uniqueness; cleanup in fixture teardown; secrets from the CI secret store and never from the repository; and specific scenario fixtures for screening outcomes such as a sanctions hit or a PEP match.

2.7 Accessibility, visual and emulation

Your resume mentions accessibility testing. How do you actually do it?

Tested: whether the claim holds. Answer precisely and stay inside your evidence.

Automated scanning with axe-core through the Playwright integration, run per key page or state, with violations attached to the test report. Be clear that automated scanning catches only a portion of issues and that keyboard navigation, focus order and screen-reader checks remain manual. Role-based locators and accessible-name assertions give continuous low-level feedback; aria snapshots assert the accessibility tree structure. Note that the old built-in accessibility API was removed, so axe is the current route — referencing page.accessibility dates you.

How do visual comparisons work and when are they worth it?

toHaveScreenshot captures, waits for stabilisation, and compares against a golden image with a configurable pixel tolerance, masking dynamic regions. Worth it for design systems and high-value layouts; expensive elsewhere, because goldens must be generated on the same OS and browser as CI, which usually means generating them inside the Docker image or in a CI job.

What can you emulate?

Viewport and device descriptors, locale and timezone, geolocation, permissions, colour scheme, reduced motion, forced colours and contrast, and offline state. Locale and timezone matter for the Nordic markets; reduced motion and forced colours extend accessibility coverage.

2.8 Process, leadership and collaboration

How do you decide what to automate?

Risk and repetition. Regulatory and money-path flows first, then high-frequency regression, then stable high-value journeys. Do not automate unstable features, one-off exploratory findings, or anything where maintenance cost exceeds the manual cost.

How do you introduce Playwright into a team that uses something else?

Start with a thin vertical slice on a single high-value journey; prove it in the pipeline; measure run time and failure-signal quality against the incumbent; keep both suites running during migration; migrate by risk order rather than alphabetically; and invest early in developer onboarding so the suite does not become one person's property.

A developer says your test is flaky and the feature is fine. How do you respond?

Be evidence-led rather than defensive. Open the trace together. It is often a real race condition users would hit occasionally, which turns the conversation into a shared defect rather than a test problem. If it is the test, fix it and say so plainly.

How do you work with developers on testability?

Negotiate stable test ids and accessible names as a contract; ask for seeding endpoints and feature flags; get deterministic hooks for time and randomness; review pull requests for testability, not only for test code. Cite the on-call work — reading logs alongside developers is the same collaboration muscle.

Tell me about a time you found a critical defect late.

Use a real situation, state the impact plainly, then focus on what changed in the process afterwards. Avoid blame, and avoid numbers you cannot support.

2.9 Scenario and whiteboard

Expect at least one of these. Practise them out loud.

  • Design an automation strategy for a customer-onboarding flow with identity verification, document upload and an external screening call.
  • You inherit a suite with four hundred tests, a forty per cent flake rate and a ninety-minute run. What do you do first?
  • The team wants to run end-to-end tests against production. Argue both sides, then propose a safe subset.
  • Design tests for a file upload with a progress bar and an asynchronous virus-scan result.
  • A page shows data from three services; one is slow and sometimes times out. Make the test deterministic without hiding the real risk.

2.10 Live coding drills

Commonly asked on a screen share. Practise each until you can do it without documentation.

  • A login test using role-based locators and web-first assertions, including a negative case.
  • Convert a test that uses waitForTimeout into one with no explicit waits.
  • A fixture providing a logged-in page, and an explanation of its teardown.
  • A worker-scoped fixture that creates and deletes a test account.
  • Intercept an endpoint and return fixed JSON, then assert the empty state and the error state of the same component.
  • Assert on a dynamic table: row count, one row selected by its text, and a button inside that row.
  • A custom matcher with expect.extend.
  • A playwright.config.ts for a three-browser matrix with an auth setup project — justifying every option you set.

2.11 Questions to ask them

  • What does the current suite's run time and flake rate look like, and who owns it?
  • How do developers and testers split responsibility for end-to-end tests?
  • Is there a test id contract with the front-end team, or is it ad hoc?
  • How do test results feed release decisions?
  • What is the hardest thing to test in this product right now?

3. How to use this plan

The goal is not to memorise answers. It is to make the resume claim true at depth: build a real framework, hit real failures, and be able to explain every decision out loud with a trade-off attached.

  1. Never state an experience you did not have. Convert every gap into either "I have not used that; here is the closest thing I have done and how I would approach it", or into real practice in the proof project before the interview.
  2. Learn every topic twice: once by reading, once by breaking something and fixing it. Only the second pass survives follow-up questions.
  3. Record a one-paragraph answer out loud for every question you cannot answer fluently, then re-listen and cut the filler.

5. The interviewer's mental model

An engineer with two solid Playwright years answers differently from a beginner in five specific ways. Aim every answer at these.

  1. They talk about locators and auto-waiting as a design contract with developers, not as syntax.
  2. They reach for fixtures and projects when asked about structure, not for base classes and inheritance.
  3. They treat flakiness as a diagnosable defect, name the category, and open the trace before touching the retry count.
  4. They can explain CI economics: workers, shards, browser downloads, run time, artifact size, and what they cut when the pipeline got slow.
  5. They hold opinions with trade-offs. "It depends" followed by the actual deciding factor is a senior answer; "it depends" alone is not.

6. Strategic approach: four tracks

Run these in parallel, not in sequence. Interview questions usually pull from more than one at a time.

Track A — language fluency

TypeScript to the point where you can read an unfamiliar fixture file and explain what the types are doing, and async semantics deeply enough to explain why a missing await produces a silently passing test.

Track B — framework craft

Design, build and then refactor a real framework. The refactor matters more than the build, because interviewers ask "what would you change" and only someone who has already changed it answers well.

Track C — failure forensics

Deliberately create flaky and failing tests, then diagnose them with traces, UI mode and reporter output. Build a personal taxonomy of causes.

Track D — narrative and process

Convert real Resurs Bank, Model N and Bookwow experience into short, specific, honest stories. Pair test-management strength with Playwright so you are not competing only on tool depth, where you are newer, but on quality ownership, where you are strong.

7. Tactical plan: five phases with exit criteria

Adjust the pace to your availability. Do not move on until the exit criterion is met, because the exit criteria are what interviewers actually test.

Phase 1 — TypeScript that survives follow-up questions

Study: structural typing; interface versus type; generics and constraints; narrowing and discriminated unions; unknown versus any; strict mode; promises and floating promises; modules and path aliases; ESLint and tsc --noEmit.

Do: convert an existing JavaScript or Java helper into strict TypeScript with no any; write a typed test-data builder using generics and a union type for customer risk categories.

Exit: explain unaided why test.extend takes two type parameters, and what happens to types when you call mergeTests.

Phase 2 — Playwright fundamentals with the "why"

Study: everything in section 1, plus locator operators, expect.poll, expect.toPass, soft assertions, expect.configure and custom matchers.

Do: rewrite a Selenium test you know well in Playwright and list every explicit wait you deleted and why. Break strict mode on purpose, read the error, fix it three ways, and decide which you would defend.

Exit: list the actionability checks unaided and explain what "stable" means for an animating element.

Phase 3 — framework architecture

Study: fixture scopes, auto, option, fixture timeouts, box, teardown order, mergeTests; page objects as fixture-supplied collaborators; projects, dependencies and teardown; storage-state authentication; timeouts; test-data strategy; tags and annotations mapped to Xray.

Do: build the proof project in section 8.

Exit: draw the framework layering on a whiteboard in under two minutes and justify each seam.

Phase 4 — reliability, CI and forensics

Study: the parallelism model; worker and parallel index; retries and retry strategy; maxFailures; trace modes; trace viewer; UI mode; reporters including blob and merge; sharding; Docker and OS consistency.

Do: introduce five flaky tests deliberately — a re-render race, a shared backend record, an animation, a time-dependent assertion and an unmocked third-party call — and fix each properly. Then run the suite sharded across a matrix, merge blob reports into one HTML report and publish it as an artifact.

Exit: given a failing trace, narrate the diagnosis out loud in senior order: what the test intended, what the DOM showed at the failing action, what the network did, then the fix.

Phase 5 — breadth, depth and rehearsal

Study: routing and HAR replay; the request fixture versus page.request; axe-core accessibility and aria snapshots; visual comparison; clock control; emulation; component testing boundaries; and the current release surface including test locks, visible-only locators, aria and screen snapshots in traces, and the Playwright test agents.

Do: at least three recorded mock interviews using section 2.

Exit: no question in the bank produces a blank pause.

Layering to be able to draw

Spec files — intent only, no selectors, no setup
Fixtures — environment and collaborators, scoped and torn down
Page and component objects — user-facing interactions  |  API client and data builders — arrange state
Playwright locators and web-first assertions
CI — projects, shards, traces, merged report

Deliberate decisions, because each one is an interview question

  • Assertions in specs, not page objects, so a failing test reads as intent. Be ready to argue the opposite too.
  • Data setup through the API, never the UI, except when the signup UI is itself under test.
  • A setup project producing storageState, with worker-scoped accounts for tests that mutate profile data.
  • Test ids agreed with developers as a contract, role-based locators preferred where the accessible name is stable.
  • fullyParallel on, serial mode nowhere, a named lock only for a genuinely shared resource.
  • Traces on first retry, video off by default, screenshots only on failure.
  • Smoke tagged and run on every pull request; full regression sharded nightly.
  • tsc --noEmit and ESLint as pipeline gates before tests run.

Do the part most candidates skip. Write a short DECISIONS.md in that project listing each choice, the alternative you rejected, and why. Interview answers fall out of that file almost verbatim.

9. Answers that cost interviews

Eliminate these, and correct yourself if one slips out.

  • "I add waitForTimeout when the page is slow." Say auto-waiting, web-first assertions, expect.poll and route waiting instead.
  • "I mostly use XPath because it is more powerful." This dates you and signals brittle suites.
  • "We just increase retries when tests are flaky."
  • "Playwright is faster than Selenium." Say why: fewer round trips, cheap contexts, built-in waiting, parallel workers by default.
  • "Our automation gives us full coverage." Coverage claims without a basis are the fastest way to lose a senior interviewer.
  • Inflating your Playwright history. Give the real answer and pivot immediately to depth.

10. Handling the experience gap honestly

You will be asked how long you have used Playwright. Prepare one calm, truthful sentence followed by evidence of depth.

  1. State the real scope of your Playwright work plainly.
  2. Immediately give a concrete artefact: the framework, what it covers, how it runs in the pipeline, and one hard problem you solved in it.
  3. Bridge to the longer arc: nine years of test design, risk analysis, test management and API testing, plus Selenium and Cypress, which is why the tooling transfer was fast.
  4. Close with current learning, named specifically — aria snapshots, sharded reporting. Specific curiosity reads as genuine; "I love learning new things" does not.

Never claim a tool, version or feature you have not touched. If you have read about it but not used it, say exactly that and then describe how you would apply it. Interviewers respect that far more than a bluff that collapses on the follow-up question.
