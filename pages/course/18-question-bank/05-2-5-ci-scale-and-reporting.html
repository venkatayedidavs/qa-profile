2.5 CI, scale and reporting

Why this lesson is here. Scale and reporting stay with phase 4, after you can diagnose a single failure.

How do you run Playwright in CI?

Linux runners; install only the browsers actually needed, or use the official Docker image; type-check and lint gates before tests; smoke suite on every pull request; full regression sharded on a schedule; traces on first retry; HTML report and traces published as artifacts; results fed back into the test-management tool. Anchor this in the GitHub Actions and Jenkins pipelines you have already run.

Your suite takes too long. What do you do, in order?

Measure first, using the report's slowest-test view rather than intuition. Then: remove waits and sleeps; move coverage down the stack from UI to API; arrange state through the API instead of the UI; enable full parallelism; tune worker count against runner CPU; shard across machines; cut redundant cross-browser runs to the risk-justified minimum; cache dependencies and browsers; disable video and trace-everything modes.

How do you get one report out of a sharded run?

Each shard emits a blob report and uploads it as an artifact; a final job merges them with merge-reports into a single HTML report. Worth adding that the merged report can group by file and shows a timeline across shards.

Workers, shards and fullyParallel — explain the difference.

Workers are parallel processes on one machine. fullyParallel allows tests within a single file to spread across workers rather than running in declaration order. Sharding splits the suite across separate machines. They compose: shards multiply the available worker count.

How do you report quality status to stakeholders?

Lead with the nine years here. Automated pass rate is not quality. Talk about coverage against requirements, risk areas, defect trends by severity, flaky-test debt, and release readiness with explicit known risks. You maintained a quality metrics matrix at Model N — use it as the example.
