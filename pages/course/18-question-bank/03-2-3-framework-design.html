2.3 Framework design

Why this lesson is here. Framework design follows fundamentals, matching phase 3.

Walk me through the structure of your Playwright framework.

Tested: whether the structure is reasoned or copied.

Specs express intent only; fixtures supply the environment and collaborators; page and component objects hold interaction knowledge; an API client arranges state; config holds the project matrix and timeouts. Finish by naming one thing you would change today and why — that sentence is what separates a builder from a user.

Fixtures or beforeEach hooks?

Fixtures keep setup and teardown in one place, are reusable across files, are created only when a test asks for them, compose with each other, and are type safe. Hooks are fine for trivial shared navigation. Worker fixtures exist for anything expensive enough to create once per worker.

Give an example of a worker-scoped fixture.

A per-worker test account derived from the worker index, created in setup and deleted in teardown, so parallel tests never fight over the same customer record. Note that a worker fixture has its own timeout and that workers are restarted after a failure to guarantee a clean environment.

How do you handle authentication?

A setup project logs in once, saves storageState to a file, and is declared as a dependency of the browser projects, so every test starts authenticated. Where tokens live in IndexedDB rather than cookies, save that too. For tests that mutate account state, use a per-worker account instead of one shared login. Keep a small number of tests that exercise the real login UI, because storage state bypasses it.

Do page objects contain assertions?

State a position and the trade-off. Assertions in specs make failures read as violated intent and keep page objects reusable; assertions inside page objects reduce duplication for repeated compound checks. A common middle ground is exposing locators and small query methods, asserting in the spec, with a few named verification helpers for heavily repeated checks.

How do you keep a large suite maintainable?

A shared locator contract with developers; component objects for repeated widgets; fixtures instead of inheritance; tags for selection; a naming convention tied to requirements so coverage maps back to Jira and Xray; a review rule that every new test declares its level and its data needs; and a recurring pass on the slowest and flakiest tests.

How do you decide what belongs in an end-to-end test at all?

Risk, expressed as the classic test-shape argument. End-to-end tests cover journeys that cross services and carry business or regulatory consequence, such as onboarding with screening. Field validation, edge cases and permutations belong at API or component level where they run in a fraction of the time. This is where your test-management background is the differentiator — do not answer it as a tool user.

Quick-fire: test.use for per-file options; option fixtures with option: true for parameterised projects; mergeTests and mergeExpects; box: true to hide helper noise in reports; auto fixtures as global before and after hooks; project dependencies and teardown; snapshotPathTemplate.
